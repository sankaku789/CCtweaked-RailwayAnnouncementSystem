CC:Tweaked 鉄道放送システム MVP仕様書

MTRを主対象としつつ、Create系鉄道環境にも展開できる、ProjectRed入力ベースの自動放送システム。

CC:Tweaked ProjectRed Bundled Wire MTR Create対応を想定 DFPWM
基本方針

列車状態の遷移トリガーはProjectRedの1chパルス入力を正とし、現在状態はCC内部で保持する。鉄道MOD固有Adapterは放送セグメント合成用のメタデータ取得にのみ使用する。Adapterが利用不能でも簡易放送は継続する。

3. ProjectRed入力仕様

3.1 NEXTパルス入力

1線につきProjectRed入力は1chのみを必須とする。入力は現在状態そのものではなく、状態を1段進めるための立ち上がりパルスとして扱う。

ProjectRed 1ch
    ↓ pulse
CC内部 state を1段進める
現在状態NEXTパルス後主な処理
IDLEAPPROACH接近イベント生成
APPROACHPLATFORMホーム在線イベント生成
PLATFORMDEPARTURE発車イベント生成
DEPARTUREIDLE次列車待機状態へ復帰
 
IDLE
  ↓ NEXT
APPROACH
  ↓ NEXT
PLATFORM
  ↓ NEXT
DEPARTURE
  ↓ NEXT または処理完了後の自動復帰
IDLE

MVPでは、設備側から複数bitで状態値を送信せず、CC側が状態を保持する。これによりGray codeや複数bit同時立ち上がりの問題を避け、配線を最小化する。

注意:

NEXTパルスを取りこぼすとCC内部状態が1段ずれる可能性がある。MVPでは起動時をIDLEとし、DEPARTURE後の自動IDLE復帰、タイムアウトや手動リセット等の復旧手段を後から追加できる設計にする。

3.2 種別bit

使用しない。 種別・行先はMetadata Adapterから取得できた場合のみ詳細放送へ追加する。Adapterが利用不能な場合は「列車が」を用いた簡易放送へフォールバックする。

4. Track State Manager

ProjectRedのNEXTパルスをCoreへ渡し、CC内部で保持している状態を1段進めて状態遷移イベントへ変換する。

{
    track = 1,
    state = "APPROACH",
    event = "approach"
}

責務:

  • NEXTパルスの立ち上がり検出
  • CC内部stateの更新
  • 接近・在線・発車イベントの生成
  • 異常・タイムアウト等のログ記録

5. Metadata Adapter

Adapterの責務は「セグメント合成に必要な付加情報の供給」のみ。

Adapterは以下を行わない。

  • 接近・発車判定
  • ProjectRed入力
  • Speaker制御
  • 放送Queue操作

共通出力例:

{
    class = "rapid",
    destination = "central",
    route = "R01",
    source = "mtr"
}

取得不能時は nil または空metadataを返す。Composer側はそれを理由に放送自体を止めない。

5.1 MTR Adapter

MTR APIから種別・行先・路線等を取得し、共通metadata形式へ変換する。HTTP/APIが利用不能でもCoreは継続動作する。

5.2 Create Adapter

Create Train Station Peripheral等から取得可能な情報を共通metadata形式へ変換する。列車状態の判定には使用しない。

5.3 None Adapter

常にmetadataなしを返す。ProjectRed + DFPWMだけで完全動作可能にする。

6. Metadata Cache

Adapter取得結果はRAM上にキャッシュ可能。運行情報キャッシュは原則として永続化しない。

cache = {
    class = "rapid",
    destination = "central",
    route = "R01",
    fetchedAt = os.epoch("utc")
}

用途はAPI一時停止時のgraceful degradation。古い情報による誤放送を避けるためTTLを設定する。

LIVE metadata
    ↓
TTL内のcache
    ↓
metadataなし
    ↓
簡易放送

CC再起動時はキャッシュを空にし、再取得する。

7. Announcement Queue

センサーイベントから直接再生せず、意味的な放送要求をQueueへ積む。

{
    type = "approach",
    track = 1,
    createdAt = ...,
    expiresAt = ...
}

MVPではローカルQueueを使用し、基本はFCFSでよい。

最低限の機能:

  • FIFO / FCFS
  • 重複除去
  • 期限切れ放送の破棄
  • 再生中は次の放送を開始しない

}

9. Segment Resolver

論理セグメントを実際のDFPWMファイルへ解決する。

{ type = "track", value = 1 }
    ↓
/assets/track/1.dfpwm

ファイルが存在しないoptional segmentはskipする。

10. Audio Player / Speaker制御

複数Speaker接続時のズレ対策として、Speakerごとに独立した再生ループを持たせない。

Segment N
   ↓
同一chunkを全Speakerへ
   ↓
Barrier
   ↓
Segment N+1

セグメント境界を同期ポイントとして利用し、ズレの累積を抑える。

制約:

CC:TweakedのSpeaker再生経路にはサーバtick・バッファ・クライアント側再生が介在するため、Luaだけでsample単位の完全同期は保証できない。MVPでは「ズレの蓄積を抑制する」ことを目標とする。

12. 設定方針

1線1コンピュータなので、番線はconfigで指定する。ProjectRed入力はNEXTパルス用1chのみを設定する。

return {
    trackNumber = 1,

    projectred = {
        next = colors.red
    },

    adapter = "mtr",

    announcement = {
        approachMelody = true,
        arrivalMelody = false, -- default
        doorsClosing = false   -- default
    }
}

MessagePackはDBではなく、JSON相当の構造化データをコンパクトなバイナリとして保存する候補。MVPでは実装コストを増やさず、必要になった時点で導入する。

14. 共有Speaker構成

別プロジェクト扱い。

1線1コンピュータのまま、Speakerだけを共有する駅では、専用Speaker Controllerへ放送要求を送る。

1番線 CC ─┐
           ├── Announcement Request ──→ Speaker Controller
2番線 CC ─┘                            │
                                       ├─ FCFS Queue
                                       ├─ Composer
                                       └─ Player
                                            ↓
                                       Shared Speakers

この別プロジェクトでは、Speakerを複数CCから直接操作せず、所有者を1台に固定する。

メイン放送システム側では、将来的にLocal Output / Remote Outputを差し替えられる境界だけ残す。

15. 旧コードからの再利用方針

既存の startup.lua / config.lua は全廃せず、責務を分離した上で一部を再利用する。旧コードの「ProjectRed入力 → 即時再生」という密結合部分は新アーキテクチャへ置き換える。

旧実装再利用度新しい配置方針
connect_speaker() 高 io/speaker.lua peripheral.find("speaker") による複数Speaker検出を再利用する。Speaker未接続時のbusy loopは修正する。
play_audio() のファイル検証 高 audio/player.lua fs.exists() / fs.isDir() による音声ファイル検証を再利用する。
play_audio() のDFPWM読込・decode 高 audio/player.lua 16 KiB単位の読込とDFPWM decoder利用は再利用候補とする。
play_audio() のSpeaker送信 低 io/speaker.lua Speakerを1台ずつ順番に処理する旧方式は廃止し、複数Speakerを同一chunk単位で管理する方式へ書き直す。
play_voice_files() 中〜高 audio/segment.lua またはutility 番号付きDFPWMファイルの探索・ソート処理は汎用補助関数として再利用可能。ただし新Composerでは意味ベースのsegment指定を主方式とする。
audio_event() 低 廃止 / Queue・Schedulerへ統合 関数内部でtimer eventを待機して直接再生する構造は廃止し、Announcement Queue経由へ置き換える。
now_time() 高 util/log.lua ログ時刻表示用utilityとしてそのまま再利用可能。
Bundled Wire読取処理 高 io/projectred.lua rs.getBundledInput() / colors.test() の考え方を再利用し、入力はNEXTパルス1chへ簡素化する。
旧main loop 低 core/scheduler.lua 等へ再構築 入力判定と音声再生が密結合しているため、Track State / Queue / Composer / Playerへ分離して作り直す。
旧config.lua 中 新config.lua 音声パス、Redstone side等の設定分離思想は再利用し、新構成に合わせてネストした設定へ整理する。

旧コードからは「Peripheral列挙」「音声ファイル検証」「DFPWM decode」「番号付きファイル探索」「ログ時刻表示」を主に再利用する。状態管理、Queue、Composer、複数Speaker同期、main loopは新設計へ置き換える。

15.2 MVP実装時の移植優先順位

  1. connect_speaker() を io/speaker.lua へ移植。
  2. play_audio() からファイル検証・DFPWM decode部分のみを audio/player.lua へ移植。
  3. ProjectRed読取処理を io/projectred.lua へ移植し、NEXTパルス1ch仕様へ変更。
  4. now_time() をログutilityへ移植。
  5. play_voice_files() は必要に応じてsegment探索utilityとして残す。
  6. 旧main loopとaudio_event()は流用せず、新しいQueue/Schedulerへ置き換える。

16. MVP完成条件

  1. ProjectRed 1chのNEXTパルスから状態遷移を進められる。
  2. CC内部でIDLE / APPROACH / PLATFORM / DEPARTUREの状態を保持できる。
  3. 接近メロディ、接近放送、任意の到着メロディ、発車放送をQueue経由で再生できる。
  4. optional segmentを条件付きでskipできる。
  5. Adapterなしでも簡易放送が成立する。
  6. MTR / Create Adapterから取得したmetadataを放送セグメントへ反映できる。
  7. Adapter/API障害時に簡易放送へフォールバックできる。
  8. 複数Speakerへ同一音声を再生し、セグメント境界で同期を取り直せる。
  9. 到着メロディとドア閉め放送をconfigでON/OFFできる。

17. 設計原則

ProjectRed = 状態をいつ進めるか
Adapter    = 何を追加で放送できるか
Composer   = どのセグメントを並べるか
Queue      = いつ再生するか
Player     = どう鳴らすか
Speaker    = 実際の出力先

最重要原則は、放送Coreが鉄道MOD固有APIへ依存しないこと。MTR、Create、Adapterなしの各構成を同一Coreで扱えることを目標とする。

この文書は現時点のMVP仕様を整理したもので、状態同期の復旧方式、MessagePack採用、共有Speaker通信方式などは将来拡張として扱う。種別bitは使用しない。
